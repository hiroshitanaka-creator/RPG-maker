# 最初の地方の受入テスト案

対象は `docs/experience-spec-v2.md` の最初の村・洞窟・ボス・関所。実装より先に検査を作り、依頼者とレビュー担当者が内容を確認してからR-07へ登録する。この文書の観測項目とデータキーは**実装側が後のスプリントで用意するインターフェースの提案**であり、既に存在する機能とは扱わない。地名・人物名・台詞・敵の具体名・座標は決めない。

## 実行

リポジトリ直下で次を実行する。

```powershell
. ./tools/prepare_scope_env.ps1
godot --headless --path . --script res://tools/smoke_first_region.gd
```

Godot 4.7.2-stableを使う。現行コードでは失敗することが正しい。14項目すべてを表示して、最後に `FIRST_REGION_FAIL: failed=14/14`、終了コード1を返す。途中で前提が欠けても検査項目を省略せず、依存する項目を「未到達」としてFAILにする。

実ゲームのmainシーンを起動する。表示されているNew Gameボタンを実際のマウス入力で操作し、位置・方向の移動には矢印キー、会話には決定キーを送る。ゲームへ渡す座標はボタンの画面上の中心だけで、ワールド座標を書き込む操作はない。

## 判定する14項目

| ID | 確かめること |
|---|---|
| A01 | New Game操作後、`start_village` の内部にいて、パーティが1人以上いる。旧本編の `town` という位置名だけでは合格にしない。 |
| A02 | タイトルから最後の関所通過まで、内部ノードを含むシーンツリー全体で、描画フレームごとに表示中のButtonとその派生型、Label、RichTextLabel、ItemList・OptionButtonの項目、TabBarの非表示でないタブ、開いているPopupMenuの項目を調べる。LineEdit・TextEditの表示文字も含める。「世界地図へ」「本編へ」を含むラベルがあればFAILとし、全経路を通れなかった場合も不在を証明したことにはしない。 |
| A03 | 村内の移動と会話から退出まで、戦闘が始まらない。村の経路を通っていない場合や位置を観測できない場合は、戦闘0回でもPASSにしない。 |
| A04 | 仲間の会話地点を回ってから村を出る。その最初の退出を観測した時点のパーティが3人であることを確認する。 |
| A05 | 村の出口へ歩くと世界マップへ移り、入口セル＋外向き1セルの位置で外向きに立つ。退出にはメニューも決定キーも使わず、直後の無操作6フレームで村へ再突入しないことも確認する。 |
| A06 | `gate_pass` がない状態で関所の手前へ歩き、門方向へ2歩を試みる。通行証なしで門セルに立ったことを常時記録し、一度でも立てばFAILにする。2回の試行中は向こう側への侵入も検出し、試行後は必ず手前のbeforeセルにいることを確認する。 |
| A07 | 世界マップから洞窟入口へ歩いて入り、`first_cave` の1階へ移る。入口の座標も入場先もゲームデータから読む。 |
| A08 | 階段を実際に踏み、1階→2階→1階→2階の順に移る。階段上へ到着した場合は、通行可能な安全な隣接セルへ一度歩いてから戻る。 |
| A09 | 実際の洞窟データの1階・2階に、宝箱が合計3個ある。IDや同じ部屋内の位置の重複を拒否する。宝箱を開く・中身を評価する検査ではない。 |
| A10 | 洞窟1階で通常の保存ボタンを押し、別セルまで歩いてから通常のロード操作を行う。層・拠点・部屋・階・セル・向き・パーティ全員の保存状態・所持品のキー、型、値、配列順序が保存前と一致することを確認する。 |
| A11 | 2階のボス地点への到達で `first_boss` 戦が始まり、実際に勝利して `gate_pass` を得る。別の地点まで歩いてから戻り、ボス戦の開始回数が1回のままであることを確認する。 |
| A12 | 階段で1階へ戻り、出口へ歩くと世界マップの洞窟入口セル＋外向き1セルへ戻る。外向きであることと、直後の無操作6フレームで再突入しないことも確認する。 |
| A13 | 通行証を持って同じ関所の手前へ戻り、門方向へ歩いて向こう側のセルへ到達する。通行証なしの試行と同じセル・方向を使う。 |
| A14 | 全経路を、実UI・方向キー・決定キー・既存の通常戦闘操作だけで通る。位置・フラグを書かずに進めたコード構造と入力記録を確認し、経路未達の場合はPASSにしない。 |

実行順は A01、メニュー確認、A09のデータ確認、仲間・退出、A06、A07、A10、A08、A11、A12、A13。A02・A03は常時監視し、A14とともに最後に判定する。出力は実行順によらずA01〜A14の順とする。

## 読み取り専用の観測インターフェース

新しいゲーム操作用APIは要求しない。既存の問い合わせに不足する項目を追加し、位置の表現は `GameSession` の `overworld` を使う。

| 名前 | 返り値・内容 | 置き場所・現状 |
|---|---|---|
| `automation_snapshot()` | 辞書。`mode`、`walkable_cells`、`battle_input`を読む。探索modeは既存の`field`または`world`、会話は`dialogue`、戦闘は`battle`。未知のmode・全滅・診断エラーはFAIL | 実mainノード、現在は `scripts/ui/game_root.gd`。既存API |
| `GameSession.export_state()` | 辞書のコピー。`overworld`、`party`、`inventory`を読む | mainの既存`game`プロパティから参照。既存API |
| `GameSession.current_battle()` | 戦闘中の既存BattleState、なければnull | `scripts/game/game_session.gd`。読み取りだけに使う既存API |
| `overworld.active/layer/node/room/cell` | activeはtrue。layerは`world`または`interior`、nodeは拠点ID、roomは部屋の0始まり配列番号、cellは整数2要素配列 | 既存の広域保存項目を流用。世界マップではnodeは空文字、roomは0とする。v2では村内開始から接続が必要 |
| `overworld.facing` | 0=下、1=左、2=右、3=上。描画している向きと保存される向きが一致する整数 | **追加が必要な保存・観測項目**。既存画面の向きの番号を流用し、テストから `_facing` を直接読んだり書いたりしない |
| `automation_snapshot().walkable_cells` | 現在の層・部屋で、今の所持品・進行状態で歩ける全セルの配列 | 既存キー。現在は旧FIELD用。worldとinteriorにも実際の当たり判定と一致する値を提供する必要がある |
| `automation_snapshot().battle_input` | 既存の`ready:bool`、`actor:String`、`enemy:String`に`encounter_id:String`を追加 | **encounter_idだけ追加が必要**。ボスは`first_boss`、通常遭遇はそれ以外の空でないID。既存の行動予約情報を流用する |
| 表示中の文字付きControl・PopupMenu | Button（派生型含む）・Labelのtext、RichTextLabelのget_parsed_text()、ItemList・OptionButtonのget_item_text()、TabBarのget_tab_title()、開いているPopupMenuのget_item_text()。LineEdit・TextEditはtext、空ならplaceholder_text。ボタンの位置も読む | ゲーム側に新しい観測関数は作らない。親を含め非表示のControlと非表示タブは対象外。表示中の無効ボタンも対象。表示中のItemList・OptionButtonは選択状態によらず全項目を調べる |
| 洞窟の階 | `world/interiors.json`の`sites[].rooms[overworld.room].floor` | 状態側のroomを既存データへ照合する。階を重複して状態へ保存する必要はない |

位置と向きは、会話・メニュー・戦闘中にも直前の探索状態として読める必要がある。観測不足を「戦闘なし」「警告なし」等へ置き換えない。キーや返り値が不足する場合はFAILとし、未実装APIを構文上の必須参照にしてロードエラーを起こさない。

通常UIの操作には既存のラベルを再利用する。New Gameは「新しくはじめる」または現行の「新しくはじめる（3人）」、ほかは「メニュー」「現在の冒険に戻る」「セーブ」「手動セーブから再開」。表示されている有効なボタンへ入力する。将来UI名を変更する場合は、実装に合わせて無断でテストを緩めず、レビューで操作契約を合わせる。

## 実装側が提供するゲームデータ

既存の `world/interiors.json` を読む。今回このファイルは変更しない。実装側は同ファイルの`sites[].rooms[].events[]`を実際の配置・イベント処理に使い、次の`first_region`を、その実データ上の地点を結び付ける定義として追加する。合否や「通過済み」を返す自己申告フィールドにはしない。

**Point**は `{layer, node, room, cell}` の辞書。cellは `[x, y]`、roomは部屋配列の番号。**Link**は `{from: Point, to: Point}` で、fromのセルを踏んだときの実際の到着点を表す。数値の座標はテストにもこの文書にも置かない。

| キー | 必要な内容 |
|---|---|
| `first_region.version` | 1 |
| `first_region.recruits` | 2件の`{stand:Point, facing:[dx,dy]}`。start_village内部でNPCに隣接する会話位置と、NPCへ向く方向。方向キーで顔を向けても会話位置から移動しない配置を使う |
| `first_region.village_exit` | start_village内部の出口Point |
| `first_region.village_entrance` | 世界マップの`{cell:[x,y], outward:[dx,dy]}`。outwardは上下左右いずれか1セル分の方向 |
| `first_region.cave_entrance` | 同じ形式の洞窟入口。退出位置はcell＋outwardから計算する |
| `first_region.cave_spawn` | 洞窟に入った直後のPoint。first_cave・1階 |
| `first_region.cave_exit` | 洞窟から出る出口Point。first_cave・1階 |
| `first_region.stairs_down` | 1階→2階のLink |
| `first_region.stairs_up` | 2階→1階のLink。戻りの到着セルも読む |
| `first_region.save_probe` | 洞窟1階の、入場直後の保存位置とは異なるPoint。保存後に実際に位置を変えるために歩く |
| `first_region.boss` | `{point:Point, encounter_id:"first_boss"}`。first_cave・2階のボスを開始する位置 |
| `first_region.boss_revisit` | ボス位置とは異なる、first_cave・2階のPoint。倒した後、一度ここまで歩いてからボス位置へ戻る |
| `first_region.gate` | `{before:Point, cell:Point, beyond:Point}`。世界マップ上で同一直線に隣接する手前・門・向こう側の3セル |
| `first_region.doors` | 必要ならLink配列。家の中と村の外など、同じ拠点・同じ階の室間移動。不要なら空配列または省略。階段往復をこの項目で代用しない |
| `sites[].id` | 村は`start_village`、洞窟は`first_cave`。検査用の中立IDで、表示名は決めない |
| `sites[].rooms[].floor` | 洞窟には1・2の両方を定義する。内部の部屋が複数あっても、room番号から実際の階を読めるようにする |
| `sites[].rooms[].events[]` | 宝箱は`{id, kind:"treasure", cell}`。洞窟全体で3件、IDと同じ部屋内のcellは重複不可。既存events/cellの形式を利用する |
| `export_state().inventory.gate_pass` | 通行証の所持数。正の整数なら所持。未所持はキーなしまたは0 |

`walkable_cells`を使い、`smoke_first_region.gd`内の読み取り専用BFS `_route`で経路を計算する。旧スモークからBFSの関数本体だけをそのまま複写し、探索順（右・下・左・上）と返り値を維持する。旧スモークの継承・ロードへの依存はなく、旧ファイルが廃止されても経路探索は動作する。同じ階の扉をまたぐ場合はLinkの部屋グラフをたどる。目的地以外の、定義された入口・出口・階段・扉・ボス・門のセルを通過経路から除き、意図しない遷移を防ぐ。マップ内にほかの強制遷移がある場合もdoorsに定義する必要がある。

部屋、座標、扉、階段、宝箱は、このテストを合格させるためだけの別データではなく、ゲームが使う配置から提供する。現行の旧本編の地点へstart_villageという名前だけを付けて合格させない。

## 戦闘・決定性・時間

- シードは`20260925`。ゲーム開始前に標準の`seed()`を1回呼ぶ。後の遭遇実装は、移動が成立した時にこの乱数系列から抽選し、壁時計・フレーム数・内部の`randomize()`で上書きしない必要がある。テストから専用の乱数内部状態を操作するAPIは追加しない。
- 世界マップや洞窟で戦闘が始まったら、既存スモークと同じ`battle_input`を読み、`submit_player_action`の`attack`で最初の対象を攻撃し、`ready`になったら`resolve_round`する。これらは本番の通常操作口であり、勝利や報酬を直接適用する呼出しではない。
- 決定キーで台詞と戦闘表示を送る。全滅や行動不能ならFAIL。再試行、回復アイテムの注入、敵HP変更、勝敗の変更はしない。遭遇回数や頻度はアサートしない。
- BattleStateの実際の勝利状態と所持品を別々に確認する。ボス地点を離れて再訪したときは`encounter_id`で通常遭遇と区別し、ボスが再開しないことを確認する。
- 移動ごとに実ゲームの150ms制限を超える160msを待つ。速度・時計起点・`Engine.time_scale`は変更しない。保存隔離には既存`RPG_QA_SAVE_PREFIX`を使い、プロセスIDは保存先の識別だけに使用する。
- 全体の上限は180秒、入力3,000回、方向入力600回、戦闘300ターン。300秒の契約上限より余裕を持ってFAIL終了するための検査予算で、ゲームの時間配分やバランスを決める値ではない。未来の配置で不足した場合も、勝手にゲームを縮小せずレビューへ戻す。

## A14を保証する方法と判定の境界

入力処理を`_key`・`_button`・`_combat_command`へ集める。キーは上下左右と決定だけ、戦闘コマンドは攻撃とターン確定だけを許可し、すべて記録する。読み取りは既存のexport_state・automation_snapshot・current_battleと実データ・表示ノードに限る。

ゲームの`new_game`・`start_new_game`を直接呼ばず、保存・ロードも実際のUIを使う。位置・向き・HP・JP・所持品・進行フラグ・`_last_move_ms`の代入、import_state、勝利確定、隠しコマンドはコードに含めない。`SceneTree`を直接継承し、旧スモークのコードはロードせず、このテスト内へ複写した読み取り専用BFSだけを利用する。A14は入力が1回送れただけではPASSにならず、実移動・実戦闘と全経路の到達が必要である。

これはコードレビューで許可されていない書込みがないことを確認できる構造と、実行時の入力制限を組み合わせたもの。プログラム自身の自己申告だけで、任意の改変後のコードまで安全と証明する仕組みではない。

| 結果 | 意味 |
|---|---|
| PASS | 各項目が観測事実で成立し、全14項目がPASS。末尾は`FIRST_REGION_PASS: checks=14`、終了0 |
| FAIL | 未実装の観測・データ、前提未成立、進行不能、全滅、不一致、上限到達など。各項目を1行ずつ出し、末尾は`FIRST_REGION_FAIL: failed=k/14`、終了1 |
| INVALID | Parse Error、SCRIPT ERROR、Failed to load script、実行強制終了、14行や最終行の欠落など。受入条件のFAILと区別し、検査プログラム自体を直す必要がある |

現行コードでA01・A02がPASSなら弱い検査として見直す。A03やA14も、未到達を理由に空の成功へ置き換えない。独立した配置データだけが将来先行して用意された場合はA09のみPASSになり得るが、全体の合格とはしない。

## R-07差し替え時に必要な変更

1. 依頼者とレビュー担当者が、この14項目・通常入力の使用・観測項目・配置キー・予算を確認する。未実装の段階でのFAILと、検査自体のINVALIDを区別する。
2. 依頼者が `.scope-lock/spec.lock.json` のR-07の本文とverifyを、新しいスモークへ差し替える。旧テストは履歴を保持し、無断で削除しない。
3. 新しいスモークと生成されたUIDを保護対象・凍結ハッシュへ追加する。これは今回行わない。
4. `tools/run_locked_checks.py` は現在、R-07の実行証拠を`CHAPTER1_`、成功を`CHAPTER1_PASS:`で判定する。差し替え時には`FIRST_REGION_`の14個の一意なID、各判定、最終行、失敗数、終了コードを照合するよう改訂し、空実行・欠落・重複・FAIL終了をPASSにしない。
5. CIの新R-07への接続と、必要なログの保存を合わせる。既存R-01〜R-06・R-08を維持し、実装前の失敗を弱化・skip・タイムアウト延長で成功にしない。
6. その後の別スプリントでゲームを実装し、機械検査と依頼者の画面確認を行う。今回はゲーム実装、契約登録、CI接続のいずれにも進まない。
