# RPG-maker v1 受入契約

## 凍結する内容

依頼者の「scope-lock 凍結入力（RPG-maker v1）」を基準とし、[入力の転記](scope-lock-input.json)にR-01〜R-08のdone_whenとverifyを保存した。職業数は人間12・モンスター8、パーティは3〜4人。旧企画の全12職・4人固定という記述とは区別する。

目標は1周約60時間で遊び切れるv1である。2026年9月20日の依頼者の明示回答により5〜6時間から正式変更し、goalのamendmentへ記録した。新しいphase・マイルストーン・MVPは設けない。その他の非目標は維持する。元の入力は履歴として保存する。

## 依頼者が追加した受入条件

2026年9月20日に[追加受入条件AC-01〜AC-03](additional-acceptance-v1.md)を登録した。指定戦闘ごとの1,000試行で勝率40〜60%、固定試行の80%以上が10ターン以内に終了、事前列挙した保存対象のキー・型・値・配列順序の不一致0件を求める。

3条件の数値は採用済み。その後の暫定値で進める指示により、専用検査と入力を用意した。AC-01は暫定入力でFAIL、AC-02は暫定入力でPASS、AC-03は型保持の修正後に3人・4人各357状態でPASS。測定方法と状態はリンク先を正とする。scope-lock本体への追加登録は未実施であり、凍結R-01〜R-08のPASSを追加3条件の全達成とは扱わない。以下は既存の凍結契約の記録である。

## 受入テスト

| 要件 | 固定対象 | 検証する振る舞い |
|---|---|---|
| R-01 | `test/unit/test_job_data.gd` | 実ファイル20件、12/8の区分、必須キー、重複、数値・参照先、実ゲームによる定義の使用。 |
| R-02 | `test/unit/test_job_change.gd` | 実戦闘の勝利でJPを加算、二重報酬なし、閾値直前からマスターへ遷移、転職後の習得保持、全滅時はJPなし。 |
| R-03 | `test/unit/test_ability_slots.gd` | 未習得技・重複・上限超過の拒否、失敗時に状態不変、装着時は技が実ダメージを発生させ、外すと戦闘へ投入できない。 |
| R-04 | `test/unit/test_monster_form.gd` | 8つすべてのモンスター職でマスター・能力変化・使用可能技・誤った解除条件の拒否・定義した条件での解除。 |
| R-05 | `test/unit/test_battle_loop.gd` | 3人・4人双方の戦闘、全ターンのシード再現性、物理ダメージと防御、行動順、実ダメージによる勝利と全滅。 |
| R-06 | `test/unit/test_save_roundtrip.gd` | 成長・魔物化・装着・所持品・進行フラグを変更した状態を実ファイルへ保存し、別インスタンスへロードして完全一致。破損ファイルでは現在状態を壊さない。 |
| R-07 | `tools/smoke_chapter1.gd` | 実際の起動シーンをロードし、通常操作の入口から移動・会話・戦闘を行って第1章へ到達。クリアフラグを直接設定しない。停止や全滅で非0終了。 |
| R-08 | `test/unit/` 全体 | 上記の全ユニットテストと、実際の起動を別プロセスで実行する`test_startup.gd`。起動時のERROR・WARNINGも失敗。 |

共通のテスト補助は `test/support/game_test.gd`。実装モジュールを直接呼び、mockで成功を返す方式は使用しない。未実装モジュールの場合はアサートを失敗させ、そのテストを合格・skipにしない。

GUTは公式v9.6.1、コミット `c80954f47bed74a0a2c471d472c0389f98e0a8f6` を変更せず `addons/gut/` に導入した。MITライセンスも同梱する。GUTがテストを読み込めず0終了する場合への対策として、公式のpost-run機能を使う `test/support/gut_gate.gd` で空実行・pending・警告・失敗を非0終了にする。verifyのコマンド文字列は依頼者の入力と同じである。

## 初期状態と保護

凍結入力を受け取る前に、戦闘計算・行動予約・編成画面のコードを書き始めていた。これを完成品として扱わず、新しい凍結仕様の本番状態管理と20職の実装前に、全8コマンドがFAILすることを確認した。[初期記録](verification/scope-lock-baseline.json)は終了コードだけでなく、テスト実行・構文エラー・タイムアウトの有無を保存している。

最初の試行はテスト構文の不備があり、初期FAIL証拠として無効。`verification/scope-lock-attempt-001-invalid.json` に分けて保持した。凍結前の修正はGUTの関数引数数と実行対象の設定であり、比較する期待値やアサートを削っていない。

`test/`、`tools/smoke_chapter1.gd`、`data/schema/`、`.scope-lock/`、`project.godot`を保護する。ディレクトリについては、元のパス表記に加え、scope-lockのglob判定で子孫へ適用する`/**`も指定する。

予算は継続40回、同じ失敗の停滞3回。検証コマンドごとのタイムアウトはスキルの既定値300秒。テストと実装の食い違いは保護ファイルを直さず、`.scope-lock/escalations/open/ESCALATION-<要件id>.md`へ記録する。

## 導入したファイルの役割

- `.scope-lock/spec.lock.json`: 凍結契約。初期化前は空の雛形であり、空の検証成功は導入完了を意味しない。
- `.scope-lock/escalations/open/`、`resolved/`: 判断が必要な事項と、その解決記録。
- `AGENTS.md`のSCOPE-LOCK管理ブロック: スコープを削減せず、保護対象を書き換えない作業規則。依頼者が書いた管理ブロック外の本文は保持した。
- `.git/hooks/pre-commit`: verify失敗時と契約変更時にcommitを止めるローカルのフック。
- `.gitignore`の`.scope-lock/state/`: 実行途中の作業状態をGit管理から除外。
- `tools/prepare_scope_env.ps1`: このプロセスだけに固定版GodotとPythonのPATHを設定。verify自体を書き換えない。
- `tools/run_locked_checks.py`: 各verifyを逐次実行し、実結果を記録する補助。スキル本体のverify_cli.pyの代わりに達成判定を作るものではない。

## 検証範囲の限界

R-07は第1章、R-08はユニットテストと起動を検証する。全8要件がPASSしても、1周約60時間の内容量と実測の達成にはならない。内容制作、追加受入条件、実測の確認は別に残る。依頼者本人の試遊を独立した制作・検査の停止理由にしない。

アプリ側のscope-lockフックの信頼・有効状態は未確認。ローカルのpre-commitフックの設置と区別し、全ツールが強制的に保護されているとは報告しない。
